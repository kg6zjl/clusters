# Blackbox probing of ingress hosts

Every ingress host in the cluster is probed from inside the cluster over the
public hostname, so a single probe exercises DNS, Traefik routing, the TLS
certificate and the backend. A host that is announced but broken shows up in
`IngressDown` instead of being noticed by hand.

## How it works

```
IngressRoute (traefik.io/v1alpha1)  ─┐
                                     ├─► ingress-blackbox-reconciler (CronJob, */5)
Ingress (networking.k8s.io/v1)      ─┘        │  one Probe CR per host
                                              ▼
                              Probe (monitoring.coreos.com/v1)  ●  jobName: ingress-availability
                                              │
                                              ▼
                              blackbox-exporter (monitoring:9115)  ──►  https://<host>/
                                              │
                                              ▼
                              probe_success{job="ingress-availability"}
```

- **Discovery is dynamic.** The reconciler lists `IngressRoute` and `Ingress`
  objects cluster-wide, extracts every `Host(...)` from the route match rules (and
  the `spec.rules[].host` / `spec.tls[].hosts` of standard Ingresses), and
  reconciles one `Probe` per distinct host. Adding an ingress makes it probed
  within five minutes; deleting one prunes its `Probe`.
- **Why a reconciler and not Prometheus discovery.** Prometheus'
  `kubernetes_sd_configs` understands only the node/service/pod/endpoints/ingress
  roles, and 23 of the 28 hosts are declared on Traefik `IngressRoute` CRs, which
  no scrape config can enumerate. The alternative - a static target list - is
  exactly what this replaces: it covered 4 of 28 hosts.
- **Nothing is hand-listed.** There is no hostname allowlist in code and no target
  list in the Prometheus scrape config. `blackbox-exporter`'s scrape config is
  generated by the Prometheus operator from the `Probe` objects, which is what
  makes this survive chart upgrades.

## Annotation contract

Annotations go on the `IngressRoute` or `Ingress` object that declares the host.
**The default is to probe: a host is probed unless an object opts it out.**

| Annotation | Values | Default | Meaning |
| --- | --- | --- | --- |
| `blackbox.stevearnett.com/probe` | `"true"` / `"false"` | `"true"` | Set `"false"` to exclude the host. Use this for a host that is expected to be unreachable. |
| `blackbox.stevearnett.com/module` | a module in the blackbox exporter config | `http_2xx` | Override the probe module. `http_2xx_insecure` is provided for a target whose certificate the exporter does not trust. |
| `blackbox.stevearnett.com/target` | a URL | `https://<host>/` | Probe a specific URL (scheme, port or path) instead of the host root. |

To exclude a host, annotate it with the reason in a comment next to the
annotation, so the next reader knows why it is not being checked:

```yaml
  annotations:
    # <why this host is expected to be unreachable>
    blackbox.stevearnett.com/probe: "false"
```

Defaults are safe: probe-by-default means a new ingress cannot be silently
unmonitored, TLS verification stays on, and the module follows redirects (many
hosts here return a 30x, usually from oauth2-proxy, before the 200).

### Hosts declared twice

Six hosts are declared by both an `IngressRoute` and a leftover standard
`Ingress`. They are probed **once**: a host is deduplicated by name, and the
`IngressRoute` is treated as the source of truth for the override annotations
because that is the object the `external-dns` annotations live on. An opt-out on
*any* object declaring the host excludes it regardless of which object carries it.

## Operating it

```bash
# run a reconcile immediately instead of waiting for the next 5-minute tick
kubectl -n monitoring create job --from=cronjob/ingress-blackbox-reconciler reconcile-now
kubectl -n monitoring logs job/reconcile-now
# the Probes it owns
kubectl get probes -n monitoring -l app.kubernetes.io/part-of=ingress-blackbox
# every probed host and its current state
curl -s 'https://prometheus.kube.stevearnett.com/api/v1/query?query=probe_success{job="ingress-availability"}'
```

The script itself is stdlib-only and reads the same objects through the API, so
it can be run with `DRY_RUN=1` to print the plan without writing anything.

The reconciler writes only `Probe` objects, only in `monitoring`; it reads only
`IngressRoute` and `Ingress` objects. It holds no secrets.

`IngressDown` (critical, 2m) fires for any probed host that fails.
`IngressProbeReconcilerStale` (warning, 15m) fires if the reconciler stops
succeeding, which is the only way a *new* ingress could go unprobed without
anything noticing.
