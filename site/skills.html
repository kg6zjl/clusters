Boundary 4

Skills: the agent's knowledge, in git

An agent that learns something useful and forgets it at the next restart is not accumulating anything. So its procedural knowledge — how to do a task, where the sharp edges are, which command lies — is written to a repository, delivered to the pod at start, and treated exactly like the cluster manifests: a change is a pull request.

Two stores, on purpose

StoreContentsHow it is loaded
Always-loaded facts Identity, environment constants, standing conventions — small and hard-capped Injected into every request, so it must stay tiny and must hold nothing task-specific
Skills Procedures: how to do a kind of work, with the pitfalls that cost real time Loaded on demand when a task matches the skill's trigger

The split is a context-window decision with a side benefit: it gives every lesson an obvious home. If it applies to a specific kind of task, it is a skill. If it applies to everything the agent does, it is one line in the small store. Anything that is neither belongs in the repository as normal documentation.

The delivery pipeline, and the part people get wrong

skills repository  →  sync at pod start  →  the pod's skills tree
   (the truth)         (replace + delete)     (a working copy)

The sync replaces files the repository has changed and deletes files it no longer has. Deletion is the step that gets skipped, and skipping it turns the pod into a museum: a lesson removed in git keeps being read forever, and worse, an outdated copy can shadow the file that replaced it.

The second failure mode is subtler and worth designing against: anything the sync does not know about survives it. A skill that only ever existed on the pod — written during a session, never committed — is not overwritten, because the delivery step has no record of it. It sits there looking authoritative, and it walks the pod's tree forward while the repository walks backwards.

The rule that falls out of this

A lesson only counts once it is in the repository. A fix that lives on the pod's volume is one restart away from being gone, and a fix that lives only in the repository may not have arrived yet. Both halves matter: write it down, and know when the pod will actually pick it up.

What belongs in a skill

  • The trigger, first. A description that starts by saying when to load it, so the agent can match a task to the right knowledge without reading everything.
  • The mechanism, then the lesson. Why the thing works the way it does, followed by the rule that follows from it. "Always do X" without the reason gets cargo-culted; the reason is what lets it be adapted.
  • Real commands and real outputs. The endpoint that works, the one that returns an error, the exact string in the log that identifies the failure. A skill full of generalities is a search result.
  • One rule per lesson. A pile of wisdom gets skimmed; a list of sharp, separate rules gets used.
  • No incident narration. No dates, no pull-request numbers, no "we hit this on Tuesday". The lesson outlives the incident, and the incident is in the history where it belongs.
  • Depth in references, not in the main file. Long material — an endpoint catalogue, a diagnostic decision tree — lives in a linked file the agent loads only when it needs that depth.

A worked example, because it is the best argument for this page

A device had routing rules that the agent could only read through a scheduled Job, and the instruction it followed was a field whitelist: print these eight fields, nothing else. The Job ran cleanly and produced a tidy log. It could not answer the question being asked, because the answer was in a field nobody had predicted — and the only interface was that log, so the cost of the whitelist was a second pull request.

The lesson that came out of it, and went into the repository:

  • Print the objects whole, and redact by key name (anything credential-shaped) rather than by a hand-picked field list.
  • Print the union of field names across the collection on one line, so a field nobody predicted is visible at a glance.
  • Print each entry's index, because ordering may be positional — and where there is no ordering field in the object at all, say so, so nobody goes looking for it again.

That is three lines of guidance replacing a wasted round trip, written down where the next task will find it. Multiply it by every mistake the agent makes once and the value of the store becomes obvious.

The caveat, stated plainly

Knowledge in a repository is only as good as its freshness. A skill that documents an interface from six months ago is worse than no skill, because it is confidently wrong. So a skill change belongs in the same pull request as the change that invalidated it, and a skill that contradicts what the cluster actually does should be treated as a bug with a fix, not as documentation.
