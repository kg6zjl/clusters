The system

Architecture: the stack, and what guards it

Everything below exists in the running cluster today. Where a component is planned, partial, or knowingly weak, it says so.

The shape

          the cluster repository (main)
          manifests · PR + required checks · human merge
                          │  reconcile
                          ▼
          Flux: source → kustomize → helm
                          │  apply
   ┌──────────────────────▼────────────────────────────────────────────┐
   │  three nodes · MicroK8s · Calico, default-deny                    │
   │  storage: Longhorn   ingress: Traefik + external-dns              │
   │                                                                   │
   │  workloads: media, home automation, monitoring, registry, CI      │
   │  admission: Kyverno  (policy over the agent's own identity)       │
   │  scanning:  Trivy    (image CVEs → reports → Prometheus → alerts) │
   └──────────▲────────────────────────────────────────────────────────┘
              │  get / list / watch only
   ┌──────────┴───────────┐         GitHub App installation token (~1h)
   │   hermes-agent pod   │◀──────── init mints once · sidecar re-mints
   │ no secrets · no exec │
   └──────────┬───────────┘
              │  branch → commit → pull request   (the only write path)
              ▼
          back to the repository

Three mini PCs run one Kubernetes cluster. There is no host CI service and no second environment: the runners that test the repository are pods in the cluster the repository describes.

Git is the only source of truth. Nothing durable is applied by hand; a controller reconciles the cluster to match the repository, so any change that is not in a merged PR is reverted on the next reconcile. That single property is what makes an agent with real reach safe to run inside it.

The GitOps spine

  • Flux watches the repository, renders the manifests (kustomize, and Helm for the vendored charts) and applies them. Each top-level path is one Kustomization with its own interval and health checks.
  • A change reaches the cluster as a merged PR. Branch, commit, required checks on self-hosted runners, human merge, reconcile. That is the whole deployment mechanism.
  • Failure is alerted on outcome, not attempt. Flux emits an event per reconcile; those surface a first failure, and a separate rule fires only if a resource is still not Ready fifteen minutes later.

The security stack

Four layers, each doing one job. None of them is a substitute for the others.

Network — default deny

Every namespace is default-deny for ingress and egress, with the exceptions written down as policy objects. The recurring trap is that the API server is a host process, not a pod, so a namespace selector does not cover it — it needs an explicit address block. See Network.

Admission — Kyverno

Kyverno runs the standard four controllers (admission, background, cleanup, reports) and holds two policies, both over the agent's own identity:

  • The identity stays read-only. The agent's ClusterRole may not gain a verb outside get/list/watch, and its ServiceAccount may only be bound to the two read-only roles. It runs with background: true, so it also re-checks the cluster role and binding that already exist.
  • Defence in depth on the privileged calls. Requests made as the agent are denied pods/exec, serviceaccounts/token and writes to Secrets. Its RBAC withholds all three already; this holds if that RBAC is ever widened by mistake.
Both policies are in Audit, on purpose

Violations are reported in a policy report, not blocked. Audit is the state until the report shows the expected zero violations; only then does the read-only policy flip to Enforce with failurePolicy: Fail. That policy matches RBAC objects alone, so failing closed on a Kyverno outage blocks privilege changes and nothing else. The second policy stays on Ignore permanently — its webhook rules match every Secret write cluster-wide, and failing closed there would let one Kyverno outage block every credential sync in the cluster.

Scanning — Trivy

trivy-operator scans running workloads from a separate scan job per workload, using a built-in Trivy server for the image fetch. It reports HIGH and CRITICAL findings that have a fix available, and nothing else: the unfiltered list on a fat base image overruns both the apiserver's request cap and the client-server message cap, so those scans fail instead of reporting.

Results feed a Grafana dashboard and, since 2026-09-30, alert rules: a Critical in a running workload pages, High is a namespace rollup at warning, and a failed scan job or a silent operator both alert — a scan that failed writes no report, which otherwise reads as clean.

The open work is triage, not coverage

The first sweep found 44 running workloads carrying a fixable Critical. The rules exist; the backlog is real. Runtime detection (Falco) is not deployed — the admission and scan layers see intent and images, not what a process does after it starts.

Identity and secrets

Secrets live in a password manager and reach workloads only through an operator that syncs one declared item per need. No secret value is in git, and the agent cannot read a Secret at all — so the layer that would leak a credential has no credential to leak. See Secrets and Permissions.

Identity: the agent's own GitHub App

The agent no longer uses the owner's personal token. It authenticates as a GitHub App owned by the cluster owner and installed on two repositories, which makes its authorship separate from the human's — the reviewer and the author are no longer the same account.

  1. The App's private key and identifiers live in the vault and are synced into a Secret. The key is mounted only into the two minter containers, never into the agent container.
  2. An init container mints an installation token before anything else, because the skills fetch during startup needs GitHub auth. A failed mint fails the pod start rather than booting with a stale credential.
  3. A sidecar re-mints at expiry minus five minutes, writing to a shared emptyDir the agent reads fresh on every call.

The token lives about an hour. Everything the agent runs — git, the CLI wrapper, its own API scripts — already read that file path, so nothing downstream changed.

Why a sidecar, and why that is the security property

A projected Secret does not refresh a subPath mount, so an hourly rotation through a Secret would silently go stale. The sidecar keeps the rotation local to the pod and keeps the durable key out of the model-driven container: a compromise yields a token that dies within the hour, not a key that can mint more.

The alert path

rules (git) → Prometheus → Alertmanager ──┬── push notification → phone
                                          └── chat webhook      → channel
                                          │
                                          ▼
       every 5 min: the detector polls Alertmanager, HMAC-signs what
       is new, POSTs it to the agent's webhook route → an agent run
  • Rules are code. Every alert lives in the repository, is reviewed like anything else, and is measured against the real metric before it ships — several were deleted for being unable to fire.
  • Two receivers, deliberately. A push for the thing that wakes you, a chat channel for the record. Sibling routes with continue, so one leg dying does not silence the other, and the alert carries the receiver type so you can tell which leg failed.
  • The cluster can wake the agent. Alertmanager cannot sign an inbound webhook, so a small in-cluster detector reads the firing alerts and signs the request itself. An alert is announced once, keyed on its own start time; one poll starts at most one run.
  • The wake path is watched too. A detector that has not succeeded in an hour alerts, and an always-firing watchdog proves the rules are loading and the pipeline can deliver by its absence. Those are separate mechanisms so neither can hide the other.
  • An unattended run has the same limits as any other. It diagnoses, answers in the channel, and opens a PR. It cannot merge.

The price of polling is latency: the agent wakes within a poll interval, not within seconds. That buys a stateless sender in a pod recreated every five minutes.

Where this is knowingly weak

  • Registry reads are open. Images are not treated as secrets: any workload in the cluster can read any repository. Acceptable because the contents are public base images and build outputs; it would not be if a private image were pushed.
  • Admission is in Audit, not Enforce. Kyverno reports violations and blocks nothing yet. Stated on the policy itself with the exact flip condition.
  • Scan triage is behind the rate of finding. 44 running workloads currently carry a fixable Critical.
  • No runtime detection. Nothing observes process behaviour in a running container.
