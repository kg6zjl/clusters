Boundary 3

State: disposable pod, versioned brain

The pod is designed to be deleted. Everything it needs to be itself is fetched from git at startup; everything durable is either in git or on a small volume; and anything written inside the running container is understood to be temporary, including edits to the agent's own instructions.

What happens on every start

An init container runs before the agent does, and its job is to make the pod's world match git:

  1. Fetch the agent's configuration and instruction files and place them where the runtime expects them.
  2. Fetch the skills repository at its current revision and sync it over the pod's skills directory, replacing files that changed and deleting files the repository no longer has.
  3. Install or verify the command-line tools the agent relies on, and leave a marker describing exactly what was delivered.

The deletion step is the part people skip, and it is the part that keeps a skills tree from becoming a museum. Without it, a file removed in git lives on inside the pod forever, and the agent keeps reading a lesson the repository threw away. See Skills for how that goes wrong even with the deletion step present.

What survives a restart

LocationNatureLost if the pod is deleted?
The container filesystem Image plus init container output Yes — rebuilt from the image and from git, identical every time
The agent's data volume A small PVC holding config, the skills working copy, scratch space and task workspaces No — but the parts that matter are re-seeded over at start, so a stale copy is never authoritative
Scratch space Deliberately short-lived, pruned on a timer Yes, and nobody cares
Anything a task wrote into a cluster object Reconciled away unless it came from the repository Yes, by design

The consequence to internalise: an edit inside the pod is not a change. It is a draft that will be overwritten at the next start, and if it was worth making it belongs in a pull request. This is the same rule as the cluster itself, applied to the agent's own brain.

Worktree discipline, because the agent is not alone

One clone, many concurrent tasks: a chat session, a scheduled job, a background worker. If they all branch in the same checkout, they move each other's HEAD mid-task and commits land on someone else's branch. The rule that fixes it: 

git -C <shared clone> fetch origin
git -C <shared clone> worktree add <path> -b <branch> origin/main
cd <path>          # all work happens here

The shared clone exists to hold the object store and mint worktrees; it is never where work happens. If its git log does not match what you just did, another session is checked out on top of you — move to your own worktree rather than "fixing" it with a checkout. Every change also starts from a fresh origin/main: a stale base has caused duplicate pull requests and, worse, merges that reintroduced already-fixed bugs.

Two kinds of remembering

The agent's knowledge is deliberately split by how often it is needed:

  • Always-loaded facts — a small, hard-capped store for identity, environment constants and standing conventions. It is small because it is injected into every single request; when it is full you consolidate, not append.
  • Skills — procedures, loaded on demand when the task matches. Rate limits and deployment rules belong here, not in the always-loaded store.

The split is what makes an agent that works on a hundred different things still fit in a context window. It also means a lesson has a home: if it only applies while doing a particular kind of work, it is a skill, and it should be written in the repository — see Skills.

The failure mode with no self-repair

Read this before letting the agent touch its own deployment

An agent whose credentials, deployment or tooling are broken cannot fix them. It has no authority to repair the thing that gives it authority, and if the break came from its own pull request, the same review gate that protects the cluster now blocks its recovery. The rule that follows is blunt: changes to the agent's own manifests and credentials require explicit human approval, every time, including the ones that look trivial.

Prefer a distinct credential with a narrow purpose over extending the one the agent already has. And when you do change something the agent depends on, plan the recovery as a human step — merge it yourself, or be reachable.
