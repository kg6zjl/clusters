Practice

Secrets: one path in, none out

The repository is public and the agent reads logs for a living, so secrets cannot be in git, in a ConfigMap, or in an environment variable that leaks into either. There is exactly one path a credential takes into this cluster, and it is a reviewed declaration plus an operator.

The path

password manager  →  operator  →  Kubernetes Secret  →  workload (env or file)
   (the truth)      (sync)      (short-lived copy)     (never the agent's business)

Each arrow is deliberately dumb. The vault holds the value and its human-readable purpose; the operator syncs named items into the cluster on an interval; the workload consumes what it was given. Nothing in that chain is a place where a mutable copy becomes the source of truth — and nothing in it is a path the agent can walk on its own, because it holds no permission to read Secrets at all (see Permissions).

Declaring a secret is a manifest change

Adding a credential means adding a declaration that names the vault item and the field inside it. Roughly, and cheaply: 

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: my-service
  namespace: my-service
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: onepassword          # cluster-scoped store: names the vault
    kind: ClusterSecretStore
  target:
    name: my-service           # the Secret it produces
  data:
    - secretKey: MY_API_KEY    # what the workload reads
      remoteRef:
        key: my-service-api-key   # the item in the vault
        property: password        # the field in that item

Three conventions do real work here. One item per purpose, so a compromised credential has exactly one blast radius and rotation is a single edit. One field per role — a value used for two jobs should be two fields, or the rotation coupling should be written down next to the declaration that causes it. And the item name states its purpose, because the next person to read the manifest needs to know what it is for, not just that it exists.

The operator's own access is the narrowest credential in the cluster

The sync controller runs under its own service account with a role limited to reading secrets, and its credential for the vault is itself delivered as a Secret. It is a good model to copy: the component whose entire job is moving secrets is the one whose own permissions are smallest and most explicit.

Rotation, and the part everyone forgets

Rotating is a vault edit, not a cluster edit — the operator notices on its next refresh. What usually breaks is not the sync, it is the consumer: a workload that read the value into an environment variable at startup keeps the old value until it restarts. So a reload controller watches the Secret and restarts the workloads that depend on it, which turns "rotate the key" into "rotate the key and confirm the pod came back".

The order matters and is worth writing down: rotate in the vault, let the operator sync, watch the consumer restart, then revoke the old credential last — because the window between revocation and reload is where an outage lives. And treat any credential that was ever committed as compromised: the fix is rotation, not a commit that removes the line.

None out

  • The agent cannot read Secret values. Not in its own namespace, not anywhere. This is the strongest single property in the setup: an agent that cannot read a secret cannot leak it, accidentally or otherwise, and cannot be talked into it.
  • Logs are the exfiltration channel to worry about. An agent prints what it sees; a command that dumps a Secret to stdout puts the value into a transcript, a CI log, or a chat message. So the rule is absolute: never echo a secret value, and when a value has to be inspected, hash it or show a few characters.
  • A commit-time secret scan gates every change. A scanner in CI plus a pre-commit hook means a pasted key fails the build rather than going public. Expect it to pay for itself exactly once, and treat that once as a rotation.
  • CI gets its secrets the same way as anything else. The runners mount credentials declared through the same operator, so a workflow reads an environment variable it already has, and no secret value is ever copied into a CI system's own secret store — see Runners.

Credential scope: the rule that survives contact with a helpful agent

An agent with dozens of jobs will eventually hold a credential that is more powerful than the task in front of it. The rule that keeps that safe is short and absolute: a credential is used for its stated purpose and nothing else.

The sharpest real example is a billing credential — a management key whose one job is to read account spend so a dashboard can show it. It is a metrics key. It must not be used to make inference requests, to create or revoke other keys, or to be substituted for the inference key because "it worked". A key that is powerful enough to do something is not permission to do it, and a successful call is not authorisation.

Write the purpose next to the declaration, and when a task appears to need a credential outside its purpose, stop and ask. That is a five-minute conversation that prevents the worst class of incident in this whole design.
