Runners: CI as a cluster citizen

Every pipeline in this setup runs on a runner pod scheduled by the cluster it is testing. No hosted runners, no cloud CI minutes, no second environment to keep in sync. The runners are ordinary cluster citizens — which also means they inherit the cluster's own rules, and its own mistakes.

Why self-host

  • Credentials stop travelling. The runners read secrets from the cluster's own secret path — the same vault-backed operator every workload uses. No secret value is ever copied into a CI system's secret store, and a workflow just reads an environment variable it already has. In the manifests that line is explicit: the notification webhook comes from the vault, never from a repository secret.
  • The build can reach what the cluster can. Pushing an image to an internal registry, reconciling with the cluster API, reading a cluster-scoped resource: all trivial when the pipeline runs inside the cluster and impossible or painful when it does not.
  • One place to reason about trust. A pipeline is code with credentials. Having it run somewhere you already apply network policy, RBAC and resource limits is the whole point.
  • Cost and privacy follow from the above: the machines are already on.

How it actually works

A controller watches for queued jobs and creates a runner pod per job (that is the standard pattern: an autoscaling runner group, plus a deployment describing the pod shape). The parts worth copying:

  • Ephemeral runners. One pod, one job, then gone. Nothing about the previous job's filesystem or credentials survives into the next, and a wedged run cannot poison the pool.
  • Init containers that fix the environment. The Docker images mount a shared tool cache mounted read-write, then an init container enforces ownership and permissions on it before the runner starts — because the next job, running as a different user, would otherwise fail on a directory it cannot write.
  • A warm tool cache. Toolchains are pre-downloaded into the cache by a periodic job, so a build does not spend its first ninety seconds fetching a compiler. Cheap to run, and the difference between a fast pipeline and one people stop watching.
  • Registry auth with no stored credential. The build logs in to the internal registry with the runner pod's own projected ServiceAccount token. The registry verifies it against the cluster's OIDC issuer, so there is no shared password in the vault, in the workflow or anywhere else — and the identity in the registry's log is the pod that pushed.
  • Notifications from the pipeline. CI posts its own failures to the same chat channel the agent uses, so a red pipeline is visible without anyone polling anything.

The least-privilege work that got done

The runners used to be the exception to everything on this site. Their ServiceAccount was bound to a cluster role of * on * — full cluster control in every namespace — and the namespace allowed unrestricted egress. Every job inherited both, including whatever a pull request asked the pipeline to run.

That identity now holds no cluster RBAC at all: the ServiceAccount exists only so the registry can map its projected token to push rights. Egress is an explicit list — DNS, the API server, the registry behind the ingress proxy, and web ports to the outside with every private address range excluded, so the rule cannot become a path back into the cluster or the LAN.

The migration was the boring version of the plan: enumerate what the builds actually reached, write those as named rules, remove the blanket, and let a build fail loudly if a destination was missing.

What a build still inherits

The registry's pull-secret rotator is allowed to create Secrets in the runner namespace, because a create cannot be scoped by name — the object does not exist when authorization runs. Everything that can be scoped is scoped to a single name, and the grant is documented in the manifest next to the reason it exists.

Lessons from running CI this way

  • A required check that fails for reasons unrelated to the diff blocks everything. A tool that helpfully self-updates inside a container where the cached binary belongs to root will fail the job and fail the merge — for every PR, forever. Pin the tool, disable its updater in CI, and treat "the pipeline is broken for everyone" as an incident with priority over any feature.
  • A change to the pipeline is tested by the pipeline. A PR that edits the workflow definition runs the workflow, so a mistake in the YAML shows up as a failed check on the PR that introduced it — a small mercy worth relying on rather than fighting.
  • The runner needs the same network scrutiny as any pod. Every connectivity failure inside a build gets the same first question as everywhere else: what does the policy allow, and what is the A/B test that proves it?
  • Give the runners resource limits and a namespace policy like anything else. A build that can starve the node it runs on is a self-inflicted outage.
