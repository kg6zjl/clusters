Boundary 2

Network: default deny, then ask

Every namespace this agent touches is default-deny for both directions. Nothing reaches it and nothing leaves it except what an explicit, reviewed rule allows. The policy is a first-class suspect in every failure, and the policy lives in git like everything else.

Why bother when RBAC already restricts it

Read-only RBAC limits what the agent can ask the API for. It does nothing about what a compromised or confused pod can reach: a database port, an admin UI on the LAN, another tenant's service, the internet. Default-deny is what turns "the agent holds no credentials" into "the agent has nowhere to send them anyway".

It also has a quieter benefit: it makes the agent's dependencies explicit. Its egress list is the honest diagram of what it needs to do its job — DNS, the API server, its own upstreams — and anything it needs later is a visible diff in a pull request.

The agent namespace's egress list

Three kinds of rule, each with a reason:

  • DNS to the cluster's resolver — UDP and TCP on port 53, selected by the namespace label. TCP matters: a large answer over UDP gets a truncated reply, and the retry needs TCP.
  • The API server — which is where everyone gets it wrong (next section).
  • Its upstreams — the model gateway or internal services it calls, by name where they are pods and by address block where they are not. Each one is a deliberate line, because reaching an internal service is a decision and should read like one.

Ingress is the mirror image: the namespace takes traffic only from the ingress proxy or the controller that owns it, and nothing else — including nothing from other namespaces that happen to want to call it.

Cross-namespace selectors use the namespace's kubernetes.io/metadata.name label, which the control plane sets automatically. No label bookkeeping, and no rule that silently stops matching because someone renamed something.

The mistake everyone makes: the API server is not a pod

A namespaceSelector rule covers pods. The kube-apiserver is not a pod. It is a host process on the nodes. So a policy built only from namespace selectors leaves it unreachable, and the symptom sends people down the wrong path: dial tcp <service-address>:443: i/o timeout. That reads like a broken control plane. It is usually a one-line egress rule nobody wrote.

Two ipBlock rules fix it, and both are needed because the packet path differs: 

egress:
  # ClusterIP of the kubernetes service — the service CIDR on 443
  - to:
    - ipBlock:
        cidr: <service CIDR>
    ports:
    - { protocol: TCP, port: 443 }

  # Node addresses, post-DNAT, on the API server's secure port
  - to:
    - ipBlock:
        cidr: <node subnet>
    ports:
    - { protocol: TCP, port: 443 }
    - { protocol: TCP, port: <apiserver secure port> }

This exact class of bug has been found and fixed at least three times in the reference setup — once for the agent, once for the load-balancer controller, once for the dashboard — which is the argument for writing it down in the operator's instructions rather than leaving it as folklore.

Debug order: the policy comes before the packet

When something cannot reach something else, do not start at the application. Start at the policy, because in a default-deny cluster it is the likeliest cause and the cheapest to check:

  1. List the policies for the source namespace and read every egress rule. Every one.
  2. Assume a policy is the cause until disproved. "It looks like allow-all" is not disproof.
  3. Run the definitive test: the same request from the same image, twice — once from a namespace with no policy at all, once from the namespace under investigation. One works, one times out: the policy is the cause, full stop.
  4. Only after exoneration, look at DNS, endpoints, or the app's own configuration.
Tell-tales worth memorising

A selector that "used to work" is usually a label that stopped matching. A controller that cannot list its own resources after a reboot is usually the missing service-CIDR rule. A project that fetches one specific host and times out on that host alone is not the policy — it is the egress path leaving through something that cannot reach it.

The gap to close in your own setup

In the reference cluster the CI runners are the exception: their namespace carries an expedient allow-all egress. It was added to unblock image builds, it works, and it is a hole — the same reasoning that makes default-deny worth having applies to the runners too, and they are the processes that hold the widest credentials.

The honest migration is not "delete the rule". It is: enumerate what the builds actually reach (registry, package mirrors, the API server, source control), write those as explicit rules, then remove the blanket — and prove it in a PR where the required check is the build that used to depend on the blanket.

Egress is a path, not a promise

A permissive egress rule says a packet may leave. It says nothing about whether it arrives. In the reference setup the cluster's default route leaves through a router that policy-routes traffic over a tunnel, with a kill switch: if the tunnel is down, traffic stops rather than falling back to the direct route. That is the intended behaviour for a privacy-conscious network, and it means one class of failure looks exactly like a broken application: one destination times out while every other destination works.

Learn to recognise the shape of the failure. The wrong reflex — restart the app, widen the policy — costs an hour:

  • Timeouts to one host, HTTP 200 from the same pod to another host a second later → the path, not the policy and not the service.
  • The alerting pipeline reporting failures for one receiver while a second receiver keeps delivering → same class, different symptom.

The fix is an explicit exemption for the destination on the router — a route that sends just that traffic out the direct path. Two things are worth knowing before you write it:

  • Do not fix it by disabling the kill switch. That fails open for every destination in the cluster, which silently undoes the reason the tunnel exists. A destination-scoped rule is surgical; a global switch is not.
  • A hostname-scoped exemption depends on DNS. If the router matches by domain, it has to see the lookup — so the client must resolve through it. An address-scoped rule has no such dependency, and a mismatched pair (domain rule, non-router resolver) fails in the confusing way: the first attempt after the cache goes cold still takes the tunnel and times out, and the retry seconds later succeeds. That softens a failure; it does not remove it.
Paging is the destination that must not ride a tunnel it cannot reach

Alert notifications are the one flow whose failure is invisible while it matters — the system that would tell you something is wrong is the thing that is wrong. Whatever else you put behind a tunnel, route the notification destinations directly. See Paging.
