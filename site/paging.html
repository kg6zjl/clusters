Paging: two receivers, no single point of silence

An alerting pipeline is the one subsystem whose failure is invisible exactly when it matters, so it gets the most paranoid treatment in this setup: independent delivery legs, an alert that names the leg that broke, and a signal that proves the pipeline is alive by its absence.

The shape of it

metrics  →  alert rules  →  Alertmanager  →  routing tree  →  receivers
 (scrape)     (in git)        (in git)        (severity)       ├─ push notification (phone)
                                                               └─ chat webhook (context, history)

Two receivers on purpose, because they fail differently and get read differently. The push notification is for the thing that wakes you up: short, on a phone, no context. The chat webhook is for the record: a channel with history, links, threading, and a place to reply. Keeping both means the pipeline has no single delivery path to lose — and, as it turned out, that is not a theoretical benefit.

Soft failure is a property of the routing tree

Both receivers are reached by sibling routes with continue, so each alert fans out to both legs independently. One receiver being dead does not stop the other, which is what turned a real incident from "paging is down" into "half of paging is down" — a much smaller problem.

The other half of soft failure is being able to tell. You do not have to deduce it from silence: the alert about the failure carries the receiver type in its integration label. So the alert itself names the leg that died, a webhook integration is the push notification service, and a chat receiver names itself. Check the counter before you open a log: 

# which leg is failing, and whether it is failing 100% of the time
sum by (integration, reason) (increase(<notifications_failed_total>[2h]))
sum by (integration)         (increase(<notifications_total>[2h]))
  • Failures equal to the total for one integration means that leg is at zero percent, not that alerting is broken — check the other integration before saying anything.
  • A retry that succeeds one second after a failure is not a flaky receiver; it is a cold cache on the egress path (see Egress is a path).
  • A running fight with one specific destination is a routing problem, not an Alertmanager problem. Fix it on the router; leave the alerting config alone.

The alert that proves the pipeline works by firing

The best trick in the whole pipeline costs nothing: an alert that always fires. It is not noise — it is a dead-man's switch. Its absence is the signal that the rules stopped loading, the scrape died, the evaluation is broken, or the pipeline cannot deliver. Every alerting system should have one, and it should be on a route whose delivery you have deliberately proven.

Same idea, applied to silence: a mute that lives only in the alerting API does not survive a rebuild of the pipeline. If a maintenance window has to be declarative, it belongs in git as a route to a receiver that does nothing — matched on every shape the silenced host appears as, with a written reason and an expiry. Anything less and the silence is gone after the next deploy, at 3am, in the noisiest possible way.

Hygiene that keeps paging trustworthy

  • Severity routing. Warnings group; critical pages. If everything pages, nothing does.
  • Inhibit rules. One root cause should not produce nine alerts; the noisy sibling gets suppressed while the cause is waving.
  • The whole tree is one file. Routes, receivers and inhibit rules live in one reviewed object. A change that ignores an existing null route or the inhibit set will regress the exact noise problem those rules were added to solve, so read it end to end before editing.
  • A config that is rejected on reload stops every notification. One broken receiver definition is not a broken receiver; it is a broken pipeline. Prove a change with a harness that sends a test alert through the real tree, not by eyeballing the YAML.
  • Deep links. A notification that does not link to the graph or the runbook gets ignored at 3am. Fixing the link template is cheap and pays every time it fires.

Where the agent fits

The agent both consumes and produces these signals, which is worth wiring deliberately:

  • It can read the alerting pipeline's own logs and metrics — the failed-send counter above is how it found a half-broken paging path rather than guessing.
  • It narrates its own work one-way into chat. The CI pipeline posts PR and failure events to a chat channel with a webhook credential delivered from the vault. The agent does not need a chat API client, and the channel gets an audit trail of what it did without anyone asking.
  • It writes alert rules as code. A rule added for a real incident — an egress path leaving the expected route, a certificate close to expiry — is only useful if it is declared, reviewed, and therefore still there next month.

The rule the agent follows: never report a pipeline as broken on the strength of one leg. Say which leg, how often, and whether the other one is still delivering.
