Alerting

An alerting pipeline is only worth having if you still read it

The hard part isn't sending an alert. It's making sure the one that arrives at 1am is worth getting out of bed for.

The shape

metrics ──▶ rules (in git) ──▶ alertmanager ──▶ routes ──┬─▶ push notification (critical only)
                                                          ├─▶ chat channel (the record)
                                                          └─▶ security channel (policy findings)

                                              every hour: a poller reads what is firing,
                                              signs it, and wakes the agent

Rules are files in the repository. Routes, receivers and inhibit rules are one reviewed object. A change to any of it is a pull request like everything else, which means the alerting config has a history and a reviewer instead of being a thing someone fixed in a hurry.

Two receivers, on purpose

They fail differently and get read differently. A push notification is for the thing that wakes me: short, on a phone, no context. A chat channel is the record: history, links, somewhere to reply. A third channel carries policy findings from admission, because those aren't incidents and shouldn't share a feed with things that are.

The two alert receivers are sibling routes with continue, so each alert fans out to both independently and one dying doesn't silence the other. When a receiver did break, that turned "paging is down" into "half of paging is down" — a much smaller problem. The alert also names the leg that failed, so I don't have to deduce it from silence.

Severity decides who hears it

Warnings group. Criticals page. If everything pages, nothing does.

The alert that proves the pipeline works by firing

There's an alert that always fires. It isn't noise, it's a dead man's switch: its absence is the signal that the rules stopped loading, the scrape died, or the pipeline can't deliver. Any alerting system should have one, routed to a receiver you've proven works.

Silences follow the same rule. A mute that lives only in the alerting API doesn't survive a rebuild of the pipeline. If a maintenance window has to be declarative, it's a route in git matched on every shape the host appears as, with a written reason and an expiry.

The agent is the second responder, not the pager

The cluster can wake the agent on its own: an hourly job reads what's currently firing, signs the request, and posts the new alerts to a webhook on the agent. It wakes up knowing what broke, looks at the resources and logs involved, and answers in the channel. If the fix is a manifest change, it opens a pull request and stops.

The controls on that path matter because this is the thing that spends money:

  • A short allow-list by alert name. Not a severity filter — a list of the alerts where an unattended run is genuinely worth starting. Everything else still notifies me; it just never spends an agent run.
  • An hourly poll, not every five minutes. The wake path isn't the paging path. Every allow-listed alert already reaches my phone inside its own delay window, so the agent can afford to be up to an hour behind.
  • A gate so a standing alert wakes it once. The lookback window is longer than the schedule, so the same standing alert shows up in several polls in a row. Without a dedupe gate, one broken thing costs a run an hour, forever.
  • A hard ceiling. At most one run per poll: twenty-four a day, by construction.

When that path first ran, it was the dominant cost, so it was turned off and rebuilt narrower before being turned back on. The measurement that stopped it was the whole provider account for 24 hours, not this path.

The habits that keep it trustworthy

  • Measure a rule before you ship it. Every rule is checked against real metric data, and a rule that can't fire gets deleted rather than admired. A rule that can never fire is worse than no rule: it reads as coverage.
  • Test the config, not the YAML. All the rules and the routing tree are parsed and checked before merge. A config rejected on reload doesn't break one route, it stops every notification in the cluster.
  • Exempt narrowly at the source. When a legitimate process trips a detection rule, the exemption is scoped to that process, its parent, and the host. Never to a file path, and never to an image name — a generic base image is a whole class of containers, and a path is exactly what the attacker touches.
  • Notify once per problem. An alert is keyed on its own start time and announced once, and a request carries an idempotency key so an overlapping poll is dropped rather than doing the work twice.
  • Link every notification to the graph. One that doesn't link to something actionable gets ignored at 1am, and fixing the link template pays out every single time it fires.
  • Inhibit by cause. One root cause shouldn't produce nine alerts. When the cause is already waving, the symptoms go quiet.

What I've decided is not an alert

  • Reboots. The nodes patch weekly and restart. That's expected, so it's a dashboard annotation, not a page. I removed the rule that would have fired every cycle.
  • A host maintenance job touching an ssh directory. It's the operating system doing housekeeping, and the exemption can't be the directory itself, or the interesting case goes quiet too.
  • Provider balance alarms for a home lab. Excluded by name from the wake path. The rule still fires and still notifies; it just doesn't spend an agent run on a number I've decided not to act on.

Each of those is written down where the rule lives, with the date, so the next person to see the alert doesn't re-litigate it.
