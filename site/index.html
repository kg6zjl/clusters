Operating notes

An AI agent as a cluster citizen

This is how an AI agent runs inside a Kubernetes cluster. It has enough reach to diagnose and fix real problems. It has no authority to change anything without review. Everything here comes from a working setup: a home cluster run from git, where the agent holds a read-only cluster role, cannot read a single secret value, and changes the world only by opening pull requests.

Written for someone building the same thing. No addresses, hostnames, domains or credentials — mechanism, not topology.

The one idea everything else follows from

An agent that can only read the cluster is safe but useless. An agent with a kubeconfig that can write is useful and terrifying: one plausible mistake is unrecoverable, and "the model was confused" is not a rollback plan.

The way out is to separate reach from authority. The agent gets maximum reach for reading — every workload, every log, every revision, every metric — and zero authority to mutate. Its only write path is a pull request, which is reviewed, CI-checked, and merged by a human before a controller applies it. The cluster is still the agent's to fix; it just has to write down the fix and get it reviewed first.

Why this holds even when the agent is wrong

Git is the source of truth and a controller reconciles the cluster to match it. The agent cannot even hold a durable change: anything applied outside the repository is reverted on the next reconcile. So a bad idea from the agent costs a rejected PR, not an outage.

The four boundaries

Read-only, and no secrets

A cluster role with get, list, watch and nothing else, no create/update/patch/delete anywhere, and — deliberately — no access to secrets, pods/exec or token minting. It can see that a secret exists in a reference; it can never see a value.

Default deny, then ask

Every namespace is default-deny for ingress and egress. The agent's namespace gets an explicit, reviewed list: DNS, the API server, its own dependencies. A pod that cannot reach something is a policy question first, and the policy is in git like everything else.

Disposable state

The pod is designed to be killed. Config and skills are re-seeded from git on every start, work happens in a fresh worktree per task, and nothing durable lives only in the container. A destroyed pod is a restart, not a loss.

The pull request is the API

Branch, commit, PR, required checks, human merge, reconcile. The agent can open and merge its own skills repository but not the cluster one. Which of those two it may merge is a decision worth making explicitly.

What the agent can and cannot do

It canIt cannot
Read any workload, pod, log, event, PVC, NetworkPolicy, Flux object or CRD status apply, patch, delete, edit — or run helm at all
Query the metrics store directly and read the alerting pipeline's own logs Read a Secret value, exec into a container, port-forward, or mint a service account token
Push a branch and open a PR, including a one-off Job that prints what it needs Merge to the cluster repository, or change a repository setting
Reproduce a failure by running the same request from a pod it controls Reach the cluster API through any path that is not an explicitly allowed egress rule

That third row on the right is the important one: when the agent needs something it has no permission to read, the answer is a reviewed Job in the repository that reads it and logs a sanitized result — not a wider role.

Where this setup is still weak

A design document that only lists strengths is a brochure. These are open today.

  • Admission reports, it does not block. The policy that pins the agent's identity to read-only verbs runs in Audit: violations land in a report, and nothing stops a widened role. Enforcement is a deliberate one-way flip, taken once the report shows the expected zero violations.
  • Scan triage is behind the findings. The image scanner is deployed and its alerts are live; the first sweep found scores of running workloads carrying a fixable Critical. Coverage is not the problem — working through the list is.
  • Nothing watches behaviour at runtime. Admission sees intent and scanning sees images. Neither sees what a process does after it starts.

The full picture, including the parts that are weak on purpose, is on Architecture.

Letting the cluster trigger the agent

The agent can also be started by the cluster instead of by a person. A detector runs every five minutes, reads what Alertmanager is currently firing, and posts the alerts it has not announced before to a webhook route on the agent, HMAC-signed. The agent wakes up knowing what broke, examines the resources and logs involved, and answers in the notification channel. It holds the same read-only access as any other session, so the worst an unattended run can do is investigate and talk — and if the alert needs a manifest change, it opens a pull request and stops. Merging stays with the human who was asleep.

That answers the questions this page used to say had to come first, and the answers are the trust model, so they are worth stating plainly.

  • Who may trigger it. Not "anything that can reach the port". The listener is a cluster-only address, a network policy narrows callers to the namespaces with business sending, and every request must carry an HMAC signature nobody can produce without the key. The key is not in the repository; it is rendered from the vault into the sender's environment at run time.
  • What an unattended run may do. Diagnose, and propose. Read-only cluster access, no secret access, and — the part that matters — a pull request, never a merge. The prompt says so, and the credential cannot merge the cluster repository in any case.
  • How much it can start. An alert is announced once, not once per poll: the filter is the alert's own start time, and the request carries an idempotency key so an overlapping poll is dropped rather than waking the agent twice. One poll starts at most one run, which caps it at twelve wakes an hour by construction, with a per-route rate limit as a backstop for a sender that loops.
  • What happens when the trigger breaks. Its freshness is alerted on like any other scheduled job here, and that alert travels the ordinary path — Alertmanager to the notification channel. The agent noticing a problem, and the cluster noticing that the agent is no longer being woken, are deliberately two separate mechanisms, so neither failure can hide the other.

Deliberately a pull rather than a push. Alertmanager cannot sign an inbound webhook, so something in-cluster has to read the alerts and sign them itself, and polling is what makes the deduplication stateless — there is no memory to lose in a pod that is recreated every five minutes. The price is latency: the agent wakes within one poll interval, not within seconds.
