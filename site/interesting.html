Interesting bits worth stealing

Everything on this page is a pattern that survived contact with a real problem. None of it is clever for its own sake; each one replaced a mistake somebody made twice.

Runbooks that say who may run each command

The cleanest idea in the whole repository: a runbook whose commands are tagged by who is allowed to run them. Commands marked read-only are safe for anyone, agent included. Commands marked operator are writes — copying data between volumes, scaling a workload during a migration — and are explicitly for a human or an approved operator, not the agent and not the CD controller.

It works because it separates two things that look like one. GitOps covers manifests beautifully and the contents of a volume not at all: no controller can copy a live database's bytes. Writing that boundary down — in the document, next to the commands — means the agent can be handed the runbook without being handed the authority to run all of it, and a human reading it in a hurry knows which half is theirs.

Why you cannot just change a StorageClass

Three facts settle it. A claim's storage class is immutable after creation. The old volume lives on one node's disk. And its reclaim policy is usually Delete, so releasing it destroys the only copy. There is no repoint in place. Every migration is therefore:

new claim → copy → repoint the workload → verify → and only then destroy the fallback.

The discipline that makes it survivable is staging it: move the workload onto replicated storage, run it long enough to trust it, then remove the old claim in a separate change. The cost is a little disk for a while; the benefit is that the irreversible step happens after the evidence, not before. The related judgement call: leave externally shared storage (a NAS export, an SMB mount) exactly where it is. Copying a network share into local replicated volumes duplicates data and creates two sources of truth.

Two ideas from that migration that generalise

Verify with the consumer, not the volume. A copied volume that mounts is not a working application; the check is that the app reads its data and writes a new row. Keep the old thing until the new thing has been wrong once. A fallback you delete the same day is not a fallback.

Backups: "no backup" and "no permission to look" are the same answer

The backup system in this cluster describes itself with custom resources, and none of it is described in git. That made a genuine mistake possible: a list call returned nothing, and the conclusion drawn was "this volume is not backed up" — when the truth was "this identity may not read the backup objects". A protected volume and an unprotected one looked identical.

The fix was one read grant, with no write verb attached. The lesson is worth more than the grant: when a safety system's state lives only in the cluster API, the agent needs read access to it. Without the read, its report on what is protected is confidently wrong. Grant the read; keep the verbs read-only.

Scan counts are dashboards; reports are evidence

Vulnerability and misconfiguration scanners usually expose both aggregate metrics and per-object reports. The metric is what tells you the trend; the report is the only thing that lets you triage, because it carries the workload, the image, the package, the version and the fix. An agent asked "how bad is it" from a count can only invent an answer. Read the reports.

Corollary that avoids alert fatigue: a scan total is almost never the right alert. Severity plus exploitability plus "is this image actually running" is.

The read-only audit Job: getting data the agent cannot fetch

The agent's credential is deliberately narrow, so there will always be a device or system that holds an answer it cannot reach — a router, a NAS, a vendor API behind a private network. The pattern that solves this without widening anything:

  1. Write a Job into the repository that runs the query with a read-only credential synced from the vault into its namespace.
  2. Print a sanitized result to the log — whole objects, with credential-shaped keys redacted by name rather than a hand-picked field list.
  3. Let the merge create it, then read its log, which is the only interface.
  4. Delete the Job file in a follow-up change so the controller prunes the finished object. A Job that names itself for a date cannot be re-run under the same name — bump the filename instead of fighting immutability.

Two properties make this better than an interactive session: the query is a reviewed diff, and the output is what somebody else would have run. The one thing to get right is the redaction — see Permissions for why an allow-list of fields is the wrong tool. A whitelist prints exactly what the last person expected, which is precisely the field that is not the answer.

Everything that can be declared, is

  • DNS records owned by a controller that reads them from the workload manifests, with ownership rules written down so two systems never fight over one record.
  • Certificates issued and renewed by a controller, with the expiry visible in the monitoring rather than in a calendar reminder.
  • Suppressions as a route to a receiver that does nothing, so a silence survives a rebuild (see Paging).
  • The agent's own work: scheduled jobs and a ticket board, so what it is doing is visible to a human without asking it.

The payoff is not tidiness. It is that "what is the state of this system" becomes a query against the repository. The agent can answer it, and so can a reviewer — including after the person who set it up has forgotten how it works.

Terraform resources, as Kubernetes objects

Crossplane is the tool that manages things outside the cluster — GitHub webhooks, cloud resources — with Kubernetes objects, by generating custom resources from a Terraform provider. You write a managed resource shaped like the Terraform resource's arguments, point it at a credential, and a controller reconciles the real thing.

The webhook case, end to end, is a good illustration:

apiVersion: repo.github.m.upbound.io/v1alpha1
kind: RepositoryWebhook
spec:
  forProvider:
    active: true
    events: [pull_request]
    repository: clusters            # no owner field: the provider infers it from the credential
    configuration:
      - contentType: json
        urlSecretRef:               # the URL is a reference; no secret appears in this manifest
          name: discord-pull-requests-webhook
          key: url
  providerConfigRef: { name: default }

The lessons that are actually load-bearing:

  • The credential is the provider's format, not yours. The GitHub provider wants the Terraform provider's JSON blob, {"token": "…"}, so a bare token fails with "cannot unmarshal github credentials as JSON". Build the shape in the secret sync, not in the resource.
  • Scope the object, not the universe. These manage one webhook and nothing else. A managed repository resource would let the controller own the repository's settings — a far bigger promise than anyone asked for.
  • A reference beats a copied value. The webhook URL lives in the vault and the manifest points at it, so it can be rotated. The CI job this replaced had the URL pasted into a repository secret by a human, and nothing could rotate it or tell you it had gone stale.
  • Some endpoints have a suffix nobody documents. A chat platform's GitHub-compatible receiver only parses the payload when the URL ends in a particular path, so the suffix is templated on during the sync rather than stored and forgotten.
  • Read the provider's install state. A managed resource that never reconciles and a provider that was never installed look identical when you only look at the resource. The agent has read access to the provider objects so it can tell those two apart.

This is also where the next chapter starts. Outbound webhooks are declarative now, and the inbound direction is built as well: the cluster wakes the agent when something is firing — see letting the cluster trigger the agent.

Four laws this setup actually enforces

  1. Network policy is the first suspect in any connectivity failure, and the claim has to be proved with the same request from a namespace with no policy — not with a comment that a policy "looks like allow-all".
  2. A timeout to one destination while another works is a path problem, not an application problem.
  3. Anything applied outside the repository will be reverted, so the repository is where a change belongs even when it would be faster not to.
  4. The agent does not touch its own deployment, credentials or tooling without approval, because it cannot repair the thing that gives it the ability to work.
