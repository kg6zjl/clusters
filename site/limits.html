Boundary 1

Permissions: read-only, and no secrets in reach

One cluster role, one service account, one binding. The role grants get, list and watch on a long list of resources, and nothing else. The list of what it does not grant is the security model.

The shape of the role

Every rule in the role has the same verb set. There is no rule anywhere with a write verb, which makes the property auditable in one pass rather than by reading subject-by-subject: 

verbs: ["get", "list", "watch"]        # every rule, no exceptions

Breadth is fine here because the verb is narrow. Reading a NetworkPolicy cannot take the cluster down; the same cannot be said for patching a deployment. So the role covers:

  • core: pods, logs, services, endpoints and endpointslices, configmaps, namespaces, nodes, PVs and PVCs, events, quotas
  • workloads: deployments, statefulsets, daemonsets, replicasets, controllerrevisions
  • networking: networkpolicies, ingresses, ingressclasses · storage: storageclasses, CSI objects, volumes
  • the GitOps stack: kustomizations, helmreleases, sources, notification objects
  • RBAC itself, so the agent can answer "who can do this" without asking a human
  • the CRD families whose status is the only honest source of truth: cert-manager, external-secrets, the monitoring stack, Longhorn, Trivy, Flux's own operator objects, the backup CRDs, and Crossplane's provider state — the one place that tells you whether a managed object is failing or its provider was never installed
Grants that look gratuitous but are not

Each of these was added after a real diagnosis failed because the read was missing. They are the cheapest possible fix for that class of failure — a read, not a write:

  • pods/log: without it the agent can see that a pod is broken and nothing about why.
  • endpointslices as well as the legacy endpoints: the old object can be stale or skipped entirely, which is exactly how a decommissioned address survived in a service's endpoint list unnoticed.
  • customresourcedefinitions: "the CRD is missing" and "the CRD exists but is not established" look identical from a failed list; the status is what tells them apart.
  • the Prometheus custom resource: its selectors are the only place that says whether a scrape job was never rendered, or was rendered and never selected. A ServiceMonitor looks perfectly correct in both cases — that gap produced a confidently wrong root cause.
  • backup and scan CRDs: the cluster API is the only description of what is actually backed up or actually scanned. Without the read, "no backup" and "no permission to look" are the same answer, and that mistake was made too.

What is deliberately absent

Not grantedConsequence
secrets — no verb at all The agent cannot read a secret value, in any namespace, ever. It sees references and existence, never contents. Secrets arrive in workloads from a manager, not through the agent.
pods/exec, pods/attach, pods/portforward No shell inside a running container, and no tunnel to a service. Reproducing a network fault happens from a pod the agent owns the definition of, not inside yours.
serviceaccounts/token It cannot mint a fresh identity for itself or anything else. It can use the token the pod was started with, and that token carries this read-only role.
anything with create, update, patch, delete No deletes, no scaling, no drain, no rollout restart, no Job creation. The only Job it can cause to exist is one it writes into the repository.
deletecollection, impersonate, escalate No bulk destruction and no wearing someone else's hat — including the "can I do this as that service account" trick, which is a privilege-escalation surface.

The kubeconfig the agent uses is itself a committed manifest with no credentials in it: it names the in-cluster server, the cluster CA, and a tokenFile pointing at the service account token the kubelet already mounted. Nothing to expire, nothing to leak, and rotating the identity means restarting the pod.

Secrets: one path in, none out

Secrets live in a password manager and are synced into the cluster by an operator, one item per declared need. That gives two properties that matter more than convenience:

  • Nothing secret is ever in git, so a public repository is survivable.
  • The agent has no shortcut around it. Because it cannot read Secrets, the only way for a workload to get a credential is the operator's own sync — which means the agent cannot leak what it cannot read, by accident or otherwise.

Declaring a secret is a manifest change like any other: an object naming an item in the vault and the field inside it, with a refresh interval. Write the trade-offs next to the declaration. A value reused for two purposes, for instance, means rotating it rotates both. Say so in a comment, where the next person will read it.

Credential scope is not a suggestion

The rule that keeps a many-purpose agent honest: a credential is used for its stated purpose and nothing else. The sharpest real example is a billing key — an account-management credential that can read spend. It is a metrics credential. It cannot be used to make model requests, to create or revoke keys, or to be echoed anywhere. A key that is powerful enough to do something is not permission to do it, and "the call succeeded" is not evidence it was allowed.

The second key: a human for privileged actions

Read-only by default does not have to mean "helpless when something is genuinely one-time-privileged". The pattern that works is an approval gate: the agent asks, the human's client shows the exact command or change, and on approval it runs. It is worth scoping this tightly, because the failure mode is not that the human approves something wrong — it is that approval fatigue turns the gate into a formality. Keep the set of gated actions small, keep them visible, and prefer a change in the repository over an approved one-off wherever both exist.

The corollary is a hard rule about self-modification: the agent must not edit its own deployment, credentials or tooling without approval. Break that and the thing that does the work is the thing that is broken, and it cannot repair itself.

The honest caveat: needs like "run a Job that reads the gateway" are best served by writing the Job into the repository and letting the controller create it — reviewed, reproducible, and already sanitized in the PR. Reach for the approval gate when there is no repository-shaped version of the action.
