Build your own: the short version

In order, because the order matters — each step makes the next one possible, and the cheapest steps are the ones that make the expensive ones safe.

The checklist

  1. Put everything in git first, and reconcile from it. Before any agent appears, the cluster should already be described by a repository and a controller, so that a change made any other way is temporary by construction. Without this, read-only access is a cage rather than a design.
  2. Give the agent a service account with read verbs only. get, list, watch across the resource families it needs to diagnose, and not one write verb anywhere. Be generous with the reads — a missing read is what makes the agent ask a human for something it could have checked itself.
  3. Do not grant secrets, exec or token minting. These are the three that turn diagnosis into exfiltration or escape. If the agent needs something from a secret, the answer is a workload that uses it, not a wider role.
  4. Move secrets into a manager and sync them in. One path in: a vault item, an operator, a workload. Add a reloader so rotation actually reaches the process, and never let a value be printed — by the agent or by anyone.
  5. Make the namespace default-deny, then write the allow-list. DNS, the cluster API, its upstreams. Use address blocks for anything that is not a pod — especially the API server, which is a host process and invisible to a namespace selector. Prove a connection failure with the A/B test before blaming the application.
  6. Make the pod disposable and its knowledge external. Rebuild config and instructions from git at start, delete what the repository deleted, and treat anything written inside the running pod as a draft.
  7. Version the agent's skills, and read them back. A lesson goes into a repository in the same change that produced it, with the reason attached. Remove the ones that stopped being true.
  8. Make the pull request the only write path, and gate the merge. Required checks plus a human merge for the cluster repository. Then verify the reconcile — merging is not applying, and the agent's summary of its own success is not evidence.
  9. Give it a way to read what it has no credential for. The pattern: a reviewed Job in the repository, a read-only credential from the vault, sanitized output, and the file deleted afterwards so the object is pruned. That is better than widening a role and better than an interactive session.
  10. Decide who runs the writes that git cannot own. Copying a volume, migrating storage, scaling during a data move: tag those commands as operator-only in the runbook, and let the agent run the read-only half.
  11. Make the agent's own success loud and its silence loud too. An always-firing watchdog alert proves the pipeline works by its absence; sibling notification routes mean one dead leg is not a dead pager.
  12. Write the gaps down, in the same place as the design. The broad CI role, the approval fatigue, the pod-only skill copies, the single human who can revive the agent. A design that lists its weaknesses gets fixed; one that lists its features gets trusted.

The five decisions to make deliberately

DecisionWhat to weigh
Which repositories may the agent merge to? A skills or docs repository is low-risk and keeps the agent useful without a human in the loop. The cluster repository is not. Decide per repository, and remember that a repository it can merge to is a repository it can change.
Which single one-off actions get an approval gate, if any? Fewer is better. Every gated action competes for the same attention, and approval fatigue is how a gate becomes a formality.
Does the agent's knowledge live on a volume at all? A volume makes it faster and adds a second copy that can drift from the repository. If you keep one, make the repository win at every start and delete what it stopped shipping.
How does the agent narrate? One-way notifications into a channel with history give you an audit trail nobody had to ask for. Just make sure the credential for it comes from the vault, not from the CI system's secret store.
What happens when the agent is the thing that is broken? Assume it cannot fix itself, and plan a human step. Put a name on it, because "someone will notice" is not a recovery plan.

How you know it is working

  • The agent diagnoses things it was never told about, because it can read the cluster.
  • It has never asked you for a write credential — every change arrived as a pull request.
  • You can read its last twenty changes in the repository, and every one says why it happened.
  • When you did nothing for a week, the cluster was still described by the repository and the agent was still working the same way.

That is the whole trick: reach without authority, and a log of every decision in a place you can review at your own pace.
