Boundary 5

The loop: from a problem to a merged change

Reading the cluster is where the agent's authority ends. Everything it changes goes through the same path a human's change does, and the path has more steps than it looks like from the outside — which is why the mechanics are worth writing down until they are automatic.

The loop

diagnose  →  fresh worktree from main  →  branch  →  commit  →  push  →  PR
   ↑                                                                       ↓
verify the object in the cluster  ←  reconcile  ←  merge (human)  ←  required checks
  1. Diagnose from the cluster, not from the repository. Read the actual state: the object, its status, the log, the event, the metric. A change written from memory is a guess with a review attached.
  2. Start a fresh worktree off the current main. Every time. A stale base has produced duplicate pull requests and, worse, merges that reintroduced bugs somebody had already fixed.
  3. Change the smallest thing that solves the problem, and let the diff be readable: one concern per pull request, the reason in the commit message, the evidence in the description.
  4. Push and open the pull request. Then watch the required checks, because they are the only thing standing between the idea and the cluster.
  5. Merge is the human's call for the cluster repository. For the agent's own skills repository it may be the agent's — which is a decision worth making explicitly rather than discovering by accident.
  6. Wait for the reconcile, then verify the object. "Merged" is not "applied". The check is the resource's own state — revision, condition, replica count — not the merge commit.
  7. Clean up after yourself. Remove the worktree, and delete the temporary file you added for a one-off inspection so the controller prunes the object it created.

Where the loop actually costs you time

These are the failures that turn a ten-minute change into an hour. All of them are mechanical, which is exactly why they belong in a runbook rather than in someone's memory:

  • "Required status checks are expected" on merge. The branch is behind the base branch: the checks have to run again against the new base before the merge will be accepted. Rebase onto the current main and push; do not fight it.
  • A force-push that "stale info" refuses. A lease on a branch the local clone has never fetched fails before it starts. Fetch the branch, read its current commit, and pass that explicitly as the lease — or rebase and do an ordinary push.
  • A required check that fails for everybody. When the pipeline itself is broken, every pull request is blocked, including the one that would fix the problem. Fix the pipeline first, in its own change, then rebase your work on top. Chasing a red check across an unrelated diff is pure waste.
  • A pre-commit hook that refuses to commit on a stale branch. The hook is right. Stash, rebase, restore, commit — in that order, and expect to do it more than once.
  • An action that runs on the pull request but only works on main. Deployment workflows must be scoped so they do not run on a pull request, and checks that gate a merge must not depend on something that cannot happen before the merge.
  • A change to a workflow file that the agent cannot push. The App deliberately has no Workflows permission, so a PR that edits CI is rejected at push time. Either make the edit by hand or grant the permission on purpose — knowing it lets the App change the checks that gate it.

What "done" means here

  • Merged and verified. The pull request's merge commit, and then the object in the cluster showing the new state. Both, in that order.
  • No leftovers. Temporary Jobs deleted from the repository after their logs are read, worktrees removed, branches deleted by the merge.
  • The evidence quoted, not paraphrased. The check's actual output, the log line with its timestamp, the revision the controller says it applied. An agent's summary of its own success is a claim; the cluster's state is the fact.
  • Assumptions labelled. "I could not verify X because Y" is a complete and useful answer. A confident guess is not.

Guardrails are the point, not the friction

The honest note from the humans in this setup, worth repeating because it is the opposite of the usual complaint: getting to work inside a system that refuses to let you poke the cluster directly is better. The review gate is why an agent can be given real reach at all. The friction worth removing is not the gate — it is the mechanical noise around it: prompts for commands that are obviously read-only, and pipeline failures unrelated to the change.

Two rules keep the gate honest. Keep the number of approved one-off privileged actions small enough that each one gets read. And never let the agent change its own tooling without approval — see the failure mode with no self-repair.
